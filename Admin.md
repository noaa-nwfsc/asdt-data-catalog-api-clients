## Template Token Management 


For the ASDT Template repository to automatically generate and configure new repositories requires specific permission.

To perform actions like copying branch rules, assigning teams, and modifying users, the workflow requires a Personal Access Token (PAT) stored as a repository secret: specifically, `CREATE_FROM_TEMPLATE_APP_PAT` 

This guide explains how maintainers should generate, authorize, and rotate this token.

### 1. Requirements for the Token
Based on the configuration script's needs, the token must meet the following criteria:
* **Account:** It must be generated by a user account that holds administrative privileges in the target organization (`noaa-nwfsc`).
* **SSO Authorization:** The token *must* be explicitly authorized for Single Sign-On (SSO) to interact with the organization's repositories.
* **Scopes:** It requires the `repo` scope (to create repos, write branch rules, and configure users), `read:org` (to read team slugs and permissions), and `workflow` (to delete the inherited workflow file from the child repository).

### 2. Generating the Personal Access Token (PAT)
1. In GitHub, click your profile picture in the top right corner and select **Settings**.
2. Scroll down the left sidebar and click **Developer settings**.
3. Select **Personal access tokens**, then click **Tokens (classic)**.
4. Click **Generate new token** -> **Generate new token (classic)**.
5. Fill out the token details:
    * **Note:** `ASDT Template Workflow Setup Token`
    * **Expiration:** Set a reasonable expiration (e.g., 90 days or 1 year) according to your organization's security policy.
    * **Scopes:** Check the boxes for `repo`, `workflow`, and `read:org`.
6. Click **Generate token**.
7. **CRITICAL STEP:** Before leaving the page, locate the new token in the list and click the **Configure SSO** dropdown next to it. Authorize it for the `noaa-nwfsc` organization.
8. Copy the token to your clipboard. You will not be able to see it again.

### 3. Adding or Updating the Secret in the Template
1. Navigate to the template repository: `noaa-nwfsc/asdt-template`.
2. Click the **Settings** tab.
3. In the left sidebar, expand **Secrets and variables** and click **Actions**.
4. To add a new token: Click the green **New repository secret** button.
5. To update an expiring token: Click the pencil icon next to the existing `CREATE_FROM_TEMPLATE_APP_PAT`.
6. Enter `CREATE_FROM_TEMPLATE_APP_PAT` as the Name (if creating new).
7. Paste your token into the **Secret** field.
8. Click **Add secret** (or **Update secret**).

### 4. Token Rotation Process
When the token approaches its expiration date, GitHub will send an email notification to the user who created it. To rotate the token with zero downtime:
1. Generate a new token following the steps in Section 2.
2. Update the `CREATE_FROM_TEMPLATE_APP_PAT` secret in the template repository with the new token.
3. Once the new token is saved and tested, delete the old token from your personal Developer Settings.
 
 
## GitHub CLI Workflow Management
The GitHub web interface for managing workflows may have problems from time to time. 

It is officially 'bugged' for its caching the old or broken state, and refusing to re-evaluate it updates.

In these case, using the GitHub CLI (`gh`) core commands for monitoring, debugging, and cleaning up GitHub Actions workflows directly from the terminal (Bash, Cygwin,  or Linux).  They also generally, but not entirely work from the Windows `cmd prompt` and `powershell`.

### 1. How to View Workflow Status
To monitor what is currently running or review recent history:

* **List recent runs:** Displays a table of the most recent workflow executions, including their status (success, failure, in_progress) and their unique Run IDs.
  ```bash
  gh run list --limit 10
  ```
* **Watch a live workflow:** Replaces a terminal screen with a live-updating dashboard of a currently executing workflow. It exits automatically when the run finishes.
  ```bash
  gh run watch <RUN_ID>
  ```
* **Watch the *most recently triggered* workflow:** A helpful one-liner that automatically finds and watches the last workflow started withou manually copying the ID.
  ```bash
  gh run watch $(gh run list --limit 1 --json databaseId --jq '.[0].databaseId')
  ```

### 2. What to Look For in Outputs and Logs
When a workflow fails, diagnosing it quickly relies on checking the logs.

* **View failed logs only:** Dumps the exact log output for only the steps that crashed, filtering out the successful noise.
  ```bash
  gh run view <RUN_ID> --log-failed
  ```

**Key Indicators of Failure in Logs:**
* **`HTTP 403 / 404 / 422`:** Usually indicates a permissions issue (token scope, SSO authorization) or a missing required input (like a missing `-f repo_name="value"` flag).
* **`::error::`:** GitHub's specific syntax for bubbling up critical errors. This indicates that a script explicitly failed and formatted a message for the UI.
* **Exit code `1` (or any non-zero number):** Standard Bash behavior indicating a script crashed or a command inside it failed.
* **Silent YAML Failures:** If a run does not even appear in `gh run list` after a trigger it or code push, it is almost always an invisible YAML syntax error (e.g., bad indentation or hidden non-breaking spaces).

### 3. How to Identify and Remove Unneeded Workflows
Deleting a `.yml` file from a repository does **not** remove it from the GitHub Actions UI. To permanently remove a "ghost" workflow, it is necessary to delete its entire run history.

* **List all recognized workflows:** This shows active and inactive workflows, along with their IDs.
  ```bash
  gh workflow list
  ```
* **Wipe a specific workflow's history:** With a workflow name or ID from the list above, run this command to fetch all of its past runs and delete them one by one. Once the history is empty, the workflow will vanish from the UI.
  ```bash
  gh run list --workflow "Workflow Name or ID" --limit 100 --json databaseId --jq '.[].databaseId' | xargs -I {} gh run delete {}
  ```

### 4. Regular Cleanup Routine
Over time, failed runs and canceled jobs clutter the history and make it harder to find actual deployment data. 

* **Delete all failed runs:** This one-liner safely sweeps through the repository, finds the last 100 failed runs, and deletes them, leaving only successful history intact.
  ```bash
  gh run list --status failure --limit 100 --json databaseId --jq '.[].databaseId' | xargs -I {} gh run delete {}
  ```
* **Targeting specific branches:** To clean up messy history on a development branch while leaving `main` alone, append the `--branch` flag to the list command.
  ```bash
  gh run list --branch develop --status failure --limit 100 --json databaseId --jq '.[].databaseId' | xargs -I {} gh run delete {}
  ```

> **Note regarding missing repositories:** If these commands are run outside of the repository directory, or if Git is misconfigured locally, append `--repo your-org/your-repo` to the end of your `gh` commands to explicitly target the correct environment.

The three types of Github Workflows to be covered are:


* **Manual Execution (**`workflow_dispatch`**):** Allows administrators to run the workflow on demand. [cite_start]When running manually, the user is prompted to input specific variables (Repository Name and Visibility)[cite: 1, 3].

* **Mixed Mode Execution:** The work flow supports both **Manual Execution** and **Automated Execution**.

### Workflow Basics
Regardless of how the workflow is triggered (manually, automatically, or a mix of both), all approaches share the same core architecture, repository prerequisites, and authentication requirements.

#### Architecture

All approaches utilize a single job named `build-and-configure` that runs on an `ubuntu-latest` environment. The execution follows this shared sequence:

1.  **Verification**: The workflow verifies that the required authentication secret (`NEW_WORKFLOW_APP_PAT`) is present in the repository. If it is missing, the workflow logs an error and exits immediately with an exit code of 1.
2.  **Execution**: It copies the necessary shell scripts to a secure, temporary location outside the git working tree. It then executes the script (`asdt-new-workflow.sh`) to create the new repository.
3.  **Cleanup & Safety**: To prevent recursive loops, the workflow disables the factory workflow in the target child repository. It clones the new repository, announces it is renaming the factory workflow , renames `create-new-asdt-repo.yml` to `create-new-asdt-repo.yml.disabled` , commits the change, and closes the conditional logic.

#### Prerequisites

  * **Script Location**: The target template repository must contain the execution script located exactly at `.github/scripts/asdt-new-workflow.sh`.
  * **Permissions**: The user must have Admin or Maintainer privileges on the template repository to add secrets and configure workflows.

#### Authentication

> Because the workflow creates new repositories and performs cross-repository Git operations, it cannot rely on the default `GITHUB_TOKEN`. The user must configure a custom  Personal Access Token (PAT).

There are two types of GitHub Tokens `fine-grained` and `classic`.

At the current data (4/3/2026) both types may be used -- as long as the *do not* have a life time longer than ninety (90) days.


**Step-by-Step Setup `classic` tokens:**

1. Using an account with administrative permissions in the current repository, click on the user *profile picture* to access setting and go to:  
   \ \ \ \ **Settings** \> **Developer settings** \> **Personal access tokens**  
   \ \ \ \ _Note: These are **user** setting, not **repository** settings._

2. Click **Generate new token** -> **Generate new token (classic)**.
3. Fill out the token details:
    * **Note:** `SOME MEANINGFUL NAME`
    * **Expiration:** As of the current date (4/3/2026) Policy limits expirations to no more than  90 days.
    * **Scopes** (Permissions)**:** Minimally for `repo`, `workflow`, and `read:org`.
4. Click **Generate token**.
5. **CRITICAL STEP:** Before leaving the page, locate the new token in the list and click the **Configure SSO** dropdown next to it. Authorize it for the `noaa-nwfsc` organization.
6. Save the token provide, as it not be visible again.
7. After closing out of users setting, open the repository's and go to:  
   \ \ \ \ **Settings** \> **Secrets and Variable** \> **Action**  
   \ \ \ \ _Note: These are **repository** setting, not **user** settings._   
8. Create a new repository secret with a name matching the secrets used in the work flow configuation file, for example `NEW_WORKFLOW_APP_PAT` and paste the generated token.

**Step-by-Step Setup `fine-grained` tokens:**

1. Using an account with administrative permissions in the current repository, click on the user *profile picture* to access setting and go to:  
   \ \ \ \ **Settings** \> **Developer settings** \> **Personal access tokens** \> **Fine-grained tokens**  
   \ \ \ \ _Note: These are **user** setting, not **repository** settings._

2.  Set the **Resource Owner** to the target organization (typically `noaa-nwfsc`).
3.  Set **Repository Access** to **All repositories**.
4.  Grant **Read and write** permissions for **Contents**, **Workflows**, and **Administration**.
5. Save the token provide, as it not be visible again.
6. After closing out of users setting, open the repository's and go to:  
   \ \ \ \ **Settings** \> **Secrets and Variable** \> **Action**  
   \ \ \ \ _Note: These are **repository** setting, not **user** settings._
7. Create a new repository secret with a name matching the secrets used in the work flow configuation file, for example `NEW_WORKFLOW_APP_PAT` and paste the generated token.

### Workflow Types

Below are the specific steps and complete YAML configurations for the three example trigger types. 

In these example the Workflow uses a custom `bash` shell script to perform some custom operation (configuration or creation for example) on another repository, then disabling the functinoality on target repositories  to prevent recursive execution

#### <u>Automated Trigger (`push` example)</u>

This approach runs entirely in the background when code is pushed. Because it cannot collect user input, the repository name and visibility must be hardcoded or derived from the environment variables.

**Steps to Run:**

1.  Edit the YAML file below to replace `auto-generated-repo-name` with your desired automated naming convention.
2.  Push a new commit or merge a pull request into the `main` branch.
3.  The workflow triggers automatically. Navigate to the **Actions** tab to view the execution logs.

#### Job Steps

The Workflow is defined by a YAML file, such as the on below, which is run by the GitHub system on `ubuntu-latest`.

As the name of the repository involved and its visiblilty is hard coded, the job has four primary steps:

1.  **Checkout Template Repository:** Uses `actions/checkout@v4` to pull the template repository code into the runner's workspace.
2.  **Verify Secret Exists:** Runs a bash conditional `if [ -z "${{ secrets.NEW_WORKFLOW_APP_PAT }}" ]; then` to confirm the authentication token is available. If missing, it echoes an error to the runner logs and aborts via `exit 1`.
3.  **Start New Workflow (Execute Script):**  
	* Copies `.github/scripts/*.sh` to a secure temporary location  outside the git working tree.
    * Grants execution permissions (`chmod +x`).
    * Executes the script (`asdt-new-workflow.sh`), passing the target repository name and visibility as environment variables.
4.  **Disable Factory Workflow in Target Repo:**  
	* Clones the newly created child repository using the PAT.
    * Configures standard `github-actions[bot]` Git credentials.
    * Checks if `.github/workflows/create-new-asdt-repo.yml` exists.
    * If found, renames it to `create-new-asdt-repo.yml.disabled`, commits the change with a `[skip ci]` flag, and pushes it back to the child repository. This ensures the newly cloned repository does not inadvertently act as a factory itself.


**Automated Trigger Example YAML File**

```yaml
name: New Workflow (Automated)
on:
  push:
    branches:
      - main

jobs:
  build-and-configure:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Template Repository
        uses: actions/checkout@v4

      - name: Verify Secret Exists
        run: |
          if [ -z "${{ secrets.NEW_WORKFLOW_APP_PAT }}" ]; then
            echo "::error::NEW_WORKFLOW_APP_PAT is missing from the template repository secrets!"
            exit 1
          fi

      - name: Start new Workflow
        env:
          GH_TOKEN: ${{ secrets.NEW_WORKFLOW_APP_PAT }}
          TEMPLATE_REPO: ${{ github.repository }}
          NEW_REPO: ${{ github.repository_owner }}/auto-generated-repo-name
          VISIBILITY: internal
        run: |
          # Copy the script to a safe location outside the git working tree
          TEMP=/tmp/asdt-new-workflow.$$
          mkdir -p $TEMP
          cp .github/scripts/*.sh $TEMP
          chmod +x $TEMP/asdt-new-workflow.sh
          
          # Run it from the temporary location
          $TEMP/asdt-new-workflow.sh

      - name: Disable Workflow in Target Repo
        env:
          GH_TOKEN: ${{ secrets.NEW_WORKFLOW_APP_PAT }}
          NEW_REPO: ${{ github.repository_owner }}/auto-generated-repo-name
        run: |
          echo "Renaming factory workflow in child repository to .disabled..."
          git clone https://x-access-token:${GH_TOKEN}@github.com/${NEW_REPO}.git child-repo
          cd child-repo
          
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          
          if [ -f .github/workflows/create-new-asdt-repo.yml ]; then
            git mv .github/workflows/create-new-asdt-repo.yml .github/workflows/create-new-asdt-repo.yml.disabled
            git commit -m "chore: disable factory workflow in child repo [skip ci]"
            git push
          else
            echo "Workflow file not found in child repo. Skipping."
          fi
```

#### <u>Mixed Trigger</u>

This approach combines both methods. It allows manual execution with custom inputs, but if triggered automatically by a push, it seamlessly falls back to default values using GitHub Actions logical OR expression syntax (`||`).

**Steps to Run:**

  * **To run manually:** Go to the **Actions** tab, click **Run workflow**, fill in the requested inputs, and execute. It will use the provided inputs.
  * **To run automatically:** Push code to the `main` branch. The workflow will trigger, realize there are no inputs, and automatically apply the hardcoded fallback defaults (e.g., `default-auto-repo-name`).
